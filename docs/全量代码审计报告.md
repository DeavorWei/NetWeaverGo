## 5. 本轮新增代码的审计发现

以下为本轮**新引入**代码的问题与风险（#1 为 P2，其余为低危或已有兜底，按影响排序）：

| # | 级别 | 发现 | 位置 | 说明与建议 |
|---|---|---|---|---|
| 1 | **P2** | 三阶段判定路径不产生 `raw_output` 及报表产物 | `inspection_executor.go executeCheckOnly` | 单阶段路径会登记 `raw_output`（:350）并生成/登记 `inspection_report.csv`、`inspection_report.json`（:423–440）；`executeCheckOnly` 三者均未登记。判定结果不受影响，但三阶段模式下用户在任务产物列表中看不到导出报表。建议补 `createArtifactWithResult` 并同步补齐报表产物登记 |
| 2 | 低 | 采集阶段 doneSteps 精度 | `inspection_pipeline.go executeCollectUnit` | `completeUnitExecution(..., len(unit.Steps), ...)`，即使个别命令执行异常也计满。仅影响进度展示精度 |
| 3 | 低 | runDataStore 满载后静默丢弃 | `run_data_holder.go` | 超过 64MB 后 `full=true`，后续 Set 全部忽略。功能正确（Stage2/3 回退读盘与原始正则），但**无告警日志**，建议首次置 full 时打 Warn |
| 4 | 低 | 正则标志转换逻辑重复 | `ui/parse_template_service.go applyRegexFlags` vs `parser.buildRegexWithFlags` | 两处实现相同语义（m/i/s → `(?mi)`）。建议 parser 导出该函数供 ui 复用，避免未来语义漂移 |
| 5 | 低 | EchoTestPane 高亮仅覆盖根规则 | `collectParseMatches` | 树引擎只收集根规则的 SplitRegex/ParseRegex 命中；子规则（嵌套）命中需改造 `TreeEngine.fillSubResult` 透传 baseOffset（方案 §6.3.2 已备注）。当前实现已在 UI 中如实降级 |
| 6 | 信息 | `TestParseTemplateResult.matches` 依赖绑定重生成 | `EchoTestPane.vue` | Go 模型已加字段，但 Wails 绑定未重新生成，前端用交叉类型 `ResultWithMatches` 兼容。重新生成绑定后可移除 |
| 7 | 信息 | RuleTableEditor 无"上移/下移" | `RuleTableEditor.vue` | 与拆分前行为一致（原内联版本也只有增删），但方案 §6.3.1 提到上移/下移；规则顺序已由 `order` 字段承载，影响有限 |
| 8 | 信息 | `defineModel` 语法 | `EchoTestPane.vue` | 使用 Vue 3.4+ 的 `defineModel`；当前依赖 vue 3.5.25，无兼容问题 |

**未发现**：循环依赖、全局可变状态泄漏（metrics/holder 均按 RunID 隔离并有 Release）、并发问题（registry/store 均有锁并有并发测试）、脱敏旁路（导出入口均已接入阻断）。

> **闭环状态（v1.2）**：上述 8 条发现已全部闭环——#1（产物登记）、#4（正则实现收敛）、#5（子规则高亮）、#6（绑定重生成，`EchoTestPane` 交叉类型已移除）、#7（规则上移/下移）、#8（`defineModel` 保留，Vue 3.5 兼容良好）；#2、#3 一并修复。执行记录见 [`docs/全量代码审计报告-分阶段修复方案.md`](./全量代码审计报告-分阶段修复方案.md)。

## 7. 遗留事项与建议（按优先级）

### P1（建议下一迭代）
1. **metrics 前端卡片**：执行详情页新增"本次运行指标"摘要（读 `TaskRun.MetricsJSON` / 快照 `metricsJson`），后端契约已就绪。

3. **重新生成 Wails 绑定**：使 `TestParseTemplateResult.matches` 与 `UserParseTemplateVO.source` 类型化（移除 EchoTestPane 的交叉类型兼容）。

### P2（增强）
4. 子规则命中高亮：改造 `TreeEngine.fillSubResult` 透传 `baseOffset`（方案 §6.3.2 备注）。
5. RuleTableEditor 增加上移/下移（承载 `order` 字段调整）。
6. **三阶段判定路径补齐产物登记**（原 §5 发现 #1，优先级由"低"提升为 P2）：`executeCheckOnly` 补登记 `raw_output`，并同步生成与登记 `inspection_report.csv` / `inspection_report.json`，使三阶段模式与单阶段路径（`inspection_executor.go` :350、:423–440）的产物可见性一致。
7. `testdata/device/versions` 补齐至 20+ 款型（当前 11 款型样本，覆盖 9 大形态）；并扩充 Cisco 等样本内容——当前 `cisco_c9300.txt` 仅 5 行软版本、未含硬件款型文本，导致 `Model` 提取为空（根因是样本过短，非 `identifyCisco` 正则缺陷，见 §3.3）。
8. `InspectionItemText` 种子扩充（当前仅 3 条英文）。
