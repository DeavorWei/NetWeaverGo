## 0. 背景、目标与非目标

### 0.1 背景

`docs/功能模块说明书/SNMP查询模块功能和逻辑.md` 已明确划出职责边界：本工具面向**交付现场的一次性采集场景**，刻意不做轮询、Trap、趋势与 MIB 管理。这一取舍同样适用于主线 A——**新增能力必须保持"一次性、可带走、零部署、产出物导向"**。

### 0.2 现状缺口（能力 × 交付阶段映射）

| 交付阶段 | 现有支撑 | 缺口 |
|----------|----------|------|
| 准备 | 设备资产、命令组、ConfigForge、文件服务器 | 无项目隔离；命令/模板无法随项目打包带走 |
| 上架加电 | SNMP 批量上线确认、批量 Ping | 无版本/序列号/license 的自动化验收 |
| 配置下发 | 任务执行引擎、错误挂起干预 | **无 dry-run、无 undo 自动生成、无变更单** |
| 验证 | 拓扑采集 + 规划比对（仅链路维度） | **配置维度无比对、无合规检查** |
| 备份 | `BackupExecutor` 通过 SFTP 下载 startup 配置 | **仅落盘，无版本化、无 diff、无基线** |
| 验收移交 | 执行报告 CSV、比对报告 HTML/CSV/JSON | **无汇总报告，产出物散落三处** |

**核心判断**：能力已经很强，缺的是"最后一公里"——把采集/比对/备份的结果**组装成可交付的产出物**。

### 0.3 目标

| 编号 | 目标 | 可度量结果 |
|------|------|-----------|
| G1 | 配置可追溯 | 任意设备任意时刻配置可检索；两次快照/基线间差异 ≤ 10s 出结果 |
| G2 | 配置可判定 | 一键判定"现场配置是否符合设计基线"，输出 PASS/FAIL 清单 |
| G3 | 产出物可交付 | 一键生成含 拓扑+比对+合规+备份+资产 的验收报告与交付包 |
| G4 | 变更可回退 | 批量变更前自动生成 undo，失败自动回滚 |
| G5 | 验收可量化 | 版本/ESN/license/光模块/温控等自动采集并判定达标 |

### 0.4 非目标（明确不做，避免滑向 NMS）

- ❌ 7×24 轮询、性能趋势、告警、大屏
- ❌ 自研配置版本库 UI（优先复用 Git，见 §2.5）
- ❌ 通用 MIB 浏览器、Trap 接收
- ❌ 多租户/账号体系（主线 C 范畴，本期不引入）
- ❌ 自动修复配置（只给建议与 undo，不自动 `commit`）

## 1. 总体设计

### 1.1 在现有分层中的位置

严格遵循架构说明书 §8「分层解耦」原则：**新业务逻辑不进 `internal/ui/`，`ui/` 只做 Wails 桥接与视图模型转换**。

```
┌──────────────────────────────────────────────────────────────┐
│ UI 服务层 internal/ui/（仅桥接 + ViewModel 转换）              │
│  baseline_service / compliance_service / delivery_service     │
│  change_service / acceptance_service                          │
├──────────────────────────────────────────────────────────────┤
│ 新增业务层（本次主体，均独立于 Wails，可单测）                  │
│  internal/baseline/    配置快照 · 基线 · 差异                  │
│  internal/compliance/  规则集 · 检查引擎                       │
│  internal/change/      变更单 · undo 推导 · 验证 · 回滚        │
│  internal/acceptance/  验收项 · 判定引擎                       │
│  internal/delivery/    报告编排 · 渲染 · 交付包                │
├──────────────────────────────────────────────────────────────┤
│ 复用现有能力                                                   │
│  taskexec（Compiler/StageExecutor/EventBus/SnapshotHub）       │
│  executor / parser / normalize / snmp / report / logger        │
├──────────────────────────────────────────────────────────────┤
│ 数据层 repository / models / config（SQLite + GORM）           │
└──────────────────────────────────────────────────────────────┘
```

### 1.2 三条统一的设计约定

1. **一切以 Run 为单位**：所有新能力都挂 `TaskRunID`，沿用 `pending → running → completed/partial/failed/cancelled` 状态机与 `TaskArtifact` 产物索引，保证与执行历史天然打通。
2. **一切产物可索引**：新增产物类型在 `internal/taskexec/status.go` 的 `ArtifactType` 常量区追加：
   ```go
   ArtifactTypeConfigSnapshot   ArtifactType = "config_snapshot"
   ArtifactTypeComplianceReport ArtifactType = "compliance_report"
   ArtifactTypeAcceptanceReport ArtifactType = "acceptance_report"
   ArtifactTypeDeliveryReport   ArtifactType = "delivery_report"
   ArtifactTypeChangeUndoScript ArtifactType = "change_undo_script"
   ```
3. **一切差异可解释**：沿用拓扑模块 `TopologyDecisionTrace` 的思路，差异/判定结果必须携带 `Evidence + Reason`，满足交付举证要求。

### 1.3 最小侵入接入点

现有 `BackupExecutor.executeBackupUnit()` 已具备完整链路：

```
执行 startupCommand → extractNextStartupConfigPath() → SFTP 下载
  → pathManager.GetBackupConfigFilePath() → TaskArtifact{ArtifactTypeBackupConfig}
```

**A1 的接入点**：在 `createArtifactWithResult()` 之后追加一次 `baseline.Ingest(...)`，计算 SHA256 并写 `config_snapshots`。**改动 ≤ 20 行，零破坏性**。

## 2. A1 配置基线管理与漂移检测

### 2.1 概念模型

| 概念 | 定义 |
|------|------|
| **配置快照 Snapshot** | 某设备某时刻某类配置（running/startup）的一次采集结果，内容寻址（SHA256） |
| **配置基线 Baseline** | 被认定"正确"的配置来源：可为某次快照（golden）、上传的模板文件、或规则描述 |
| **漂移 Drift** | 快照 ↔ 基线 或 快照 ↔ 快照 之间的差异 |
| **忽略规则 IgnoreRule** | 排除易变内容（时间戳、crypto 密钥、计数器、NTP 漂移值） |

### 2.2 采集通道

| 通道 | 适用 | 复用 | 备注 |
|------|------|------|------|
| SFTP 下载 startup | 华为/华三/思科（已支持） | `BackupExecutor` + `sftputil` | 最可靠，文件完整 |
| CLI 回显 running | 不支持 SFTP / Telnet 设备 | `DeviceExecutor.ExecuteCommandSync` + 分页处理 | 需清洗回显头尾与 `--More--` |
| 本地上传 | 设计院给的标准配置 | 文件导入 | 作为基线来源 |

> 现状限制：`BackupExecutor` 明确拒绝 Telnet 协议（依赖 SFTP）。补 CLI 回显通道后可覆盖 Telnet 与不支持 SFTP 子系统的设备。

### 2.3 差异算法

借鉴 `plancompare` 已验证的两条经验：**先标准化再比对**、**先分类再判定严重度**。

```
raw config
  ├─ Step1 行规范化：统一 CRLF、去行尾空格、压缩连续空格
  ├─ Step2 段落切分：按缩进/视图层级构建 Section 树（interface / bgp / ospf / acl ...）
  ├─ Step3 忽略过滤：IgnoreRule（正则 + 内置预设 timestamp/secret/counter）
  ├─ Step4 键归一化：接口名 → normalize.NormalizeInterfaceName()
  ├─ Step5 层级对齐：SectionKey 相同 → 逐行 diff；SectionKey 独有 → 整段新增/缺失
  └─ Step6 分类：added / removed / modified / moved(顺序变化) / ignored
```

**关键设计**：
- **内容寻址去重**：相同内容只存一份（`config_objects` 表 + `ref_count`），100 台设备配置相同的场景节省 99% 空间。
- **段落级而非纯行级**：网络配置是层次结构，`interface GigabitEthernet0/0/1` 下缩进内容必须与其父段绑定，否则纯行 diff 会产生大量误报。
- **顺序敏感性可配置**：ACL/策略路由顺序敏感（默认 sensitive），接口段落默认 insensitive。

### 2.5 存储后端抽象（推荐先上 Git）

```go
// internal/baseline/store.go
type SnapshotStore interface {
    Put(ctx context.Context, content []byte) (hash string, path string, err error) // 内容寻址写入
    Get(ctx context.Context, hash string) ([]byte, error)
    Delete(ctx context.Context, hash string) error
    History(ctx context.Context, deviceIP string) ([]SnapshotRef, error) // 版本历史
}
```

| 实现 | 说明 | 建议 |
|------|------|------|
| `FileStore` | `netWeaverGoData/baseline/objects/<hash[:2]>/<hash>` + SQLite 索引 | 默认，零依赖 |
| `GitStore` | 备份目录 `git init`，每设备一个分支/目录，按采集时间 commit | **推荐优先**：diff/blame/回滚/历史全部复用 Git，省掉自研版本库 |

> 结论：MVP 用 `FileStore` 保证零依赖；`GitStore` 作为可选后端（设置项），因为"备份目录即 Git 仓库"对交付工程师极友好——可直接用 `git diff` 给客户看。

## 3. A2 合规基线检查

### 3.1 为什么它是最该做的功能

`docs/功能模块说明书/任务执行模块功能和逻辑.md` §8.1 的扩展示例写的就是 `ComplianceTaskCompiler` —— **扩展点已被设计者预留**。合规检查把"人工 grep 回显"变成"机器判定 + 举证清单"，是验收报告的核心内容。

### 3.2 规则模型

```go
// internal/models/compliance.go
type ComplianceRuleSet struct {
    ID          string    `gorm:"primaryKey" json:"id"`
    Name        string    `gorm:"uniqueIndex;not null" json:"name"` // "等保三级-交换机"
    Description string    `json:"description"`
    Vendor      string    `gorm:"index" json:"vendor"`
    AppliesTo   []string  `gorm:"serializer:json" json:"appliesTo"` // role 列表：access/core/...
    Version     string    `json:"version"`
    Enabled     bool      `json:"enabled"`
    CreatedAt   time.Time `json:"createdAt"`
    UpdatedAt   time.Time `json:"updatedAt"`
}

type ComplianceRule struct {
    ID            uint     `gorm:"primaryKey;autoIncrement" json:"id"`
    RuleSetID     string    `gorm:"index;not null" json:"ruleSetId"`
    Code          string    `gorm:"index" json:"code"`     // SEC-001
    Title         string    `json:"title"`                 // 必须启用 SSH，禁用 Telnet
    Category      string    `gorm:"index" json:"category"` // security / reliability / ops / naming
    Severity      string    `json:"severity"`              // blocker / major / minor / info
    CheckType     string    `json:"checkType"`             // 见下表
    Scope         string    `json:"scope"`                 // global / section
    SectionPattern string   `json:"sectionPattern"`        // section 作用域时的段落正则
    Pattern       string    `gorm:"type:text" json:"pattern"` // 匹配表达式
    Expect        string    `json:"expect"`                // 期望值（value_equals 用）
    Remediation   string    `gorm:"type:text" json:"remediation"` // 修复建议/补救命令
    Enabled       bool      `json:"enabled"`
    Tags          []string  `gorm:"serializer:json" json:"tags"`
}
```

**规则类型（CheckType）**

| 类型 | 语义 | 示例 |
|------|------|------|
| `must_contain` | 必须存在匹配行 | 必须存在 `ssh server enable` |
| `must_not_contain` | 不得存在匹配行 | 不得存在 `telnet server enable` |
| `regex_match` | 全文正则必须命中 | 密码策略 `user-password.*min-length 8` |
| `value_equals` | 指定键必须等于期望值 | `ntp-service unicast-server` 指向指定 IP |
| `count_range` | 匹配行数量在区间内 | 聚合组成员数 == 2 |
| `section_consistency` | 所有同类段落必须一致 | 所有 access 口配置相同 port-security |
| `script` | 内置小脚本（后期，CELR/表达式） | 复杂判定 |


### 5.2 变更流水线

```
draft → 预检查(precheck) → [审批] → 备份 → 下发 → 验证 → 完成
                                                ↓fail
                                            自动回滚(undo) → 复验 → 报告
```

| 阶段 | 实现 | 复用 |
|------|------|------|
| 预检查 | 采集当前快照 + 跑合规/基线 + 连通性 | **A1 / A2** / `icmp` |
| 备份 | 触发一次 Backup 任务 | `BackupExecutor` |
| 下发 | 普通命令任务（可挂起干预） | `DeviceCommandExecutor` |
| 验证 | Ping + 命令断言 + 快照 diff + 合规复检 | **A1 / A2** |
| 回滚 | 逆序执行 undo 步骤 | 新增 `ChangeExecutor` |
| 报告 | 生成变更记录章节 | **A3** |

### 5.3 undo 推导策略

```go
// internal/change/undo.go
type UndoDeriver interface {
    Derive(cmd string, vendor string) (undo string, confidence string)
}
```

| 策略 | 说明 | 置信度 |
|------|------|--------|
| 厂商模板 | 画像新增 `undo_templates`（正则 → 反向模板），如 `vlan 10` → `undo vlan 10` | high |
| 通用前缀 | 华为/华三 `undo X`、思科 `no X` | medium |
| 对称命令 | `shutdown` ↔ `undo shutdown`，`ip address X` ↔ `undo ip address X` | high |
| 无法推导 | 标记 `manual`，必须由工程师补写 | low（阻断执行） |

> **安全策略**：存在 `confidence=low` 的 undo 步骤时，变更单不允许在 `AutoUndo=true` 下执行——宁可不做，不可做错。

## 11. 分阶段实施计划

### P0 — 打通"配置可追溯 + 合规可判定"（建议 2 个迭代）

| # | 任务 | 关键交付 | 验收标准 |
|---|------|----------|----------|
| 1 | `internal/baseline` 存储与摄入 | `FileStore` + `Ingester` + 备份后自动建快照 | 备份任务完成后 `config_snapshots` 自动生成，SHA256 正确 |
| 2 | 段落解析 + diff | `section_parser` + `differ` | 3 厂商样本 golden 测试通过；1000 行配置 diff < 1s |
| 3 | 基线管理与漂移报告 | 基线 CRUD、快照↔基线/快照↔快照 diff、HTML 导出 | 能指出"这台设备与标准基线差 3 处" |
| 4 | `internal/compliance` 引擎 | 规则模型 + 5 种基本 CheckType + 内置种子 | 单设备试跑输出 PASS/FAIL + 证据行 |
| 5 | 合规编译器与执行器 | `ComplianceTaskCompiler` + `ComplianceCheckExecutor` 注册 | 批量 50 台并发检查，结果落 `task_artifacts` |

**依赖顺序**：1 → 2 → 3；2 → 4 → 5（段落解析是两者共同底座）。

### P1 — 打通"产出物可交付"与"验收可量化"

## 12. 风险与取舍

| 风险 | 影响 | 缓解 |
|------|------|------|
| 配置段落解析跨厂商差异大 | diff 误报多，用户不信任 | golden 测试覆盖三厂商；段落规则可用户扩展；提供"原始文本 diff"兜底模式 |
| 合规规则维护成本 | 规则库过时 | 规则集版本化 + 导入导出；内置种子只放跨项目通用的安全/运维基线 |
| undo 推导错误导致二次故障 | **高** | low 置信度阻断；回滚前强制快照；回滚脚本人工确认后才执行 |
| Telnet 设备无法 SFTP 备份 | A1 覆盖率不足 | 补 CLI 回显采集通道（P0 内做） |
| 报告渲染引入重依赖（PDF 引擎） | 破坏"零部署单 exe" | 一期只出 HTML/MD/CSV；PDF 走系统打印，不内置二进制 |
| SQLite 数据膨胀 | 磁盘占用 | 内容寻址去重 + 快照保留策略 + `ref_count` GC |
| 与主线 B/C 抢资源 | 摊薄 | A1+A2 是 A3 的数据源，必须先行；B/C 与 A 并行不冲突的部分（凭据加密）可提前 |

## 13. 附录：关键接口签名

```go
// ============ A1 baseline ============
type Store interface {
    Put(content []byte) (hash, path string, err error)
    Get(hash string) ([]byte, error)
    Delete(hash string) error
}

type Differ interface {
    // Diff 返回段落级差异，opts 控制忽略规则与顺序敏感性
    Diff(left, right *sections.Config, opts DiffOptions) (*DiffReport, error)
}

type Service interface {
    Ingest(ctx context.Context, runID, artifactID, deviceIP, kind, localPath string) (*ConfigSnapshot, error)
    DiffSnapshots(ctx context.Context, leftID, rightID string, opts DiffOptions) (*ConfigDiffReport, error)
    DiffAgainstBaseline(ctx context.Context, snapshotID, baselineID string, opts DiffOptions) (*ConfigDiffReport, error)
    Export(reportID string, format string) (string, error)
}

// ============ A2 compliance ============
type RuleEvaluator interface {
    Type() string
    Evaluate(ctx *EvalContext, rule *Rule) RuleResult
}

type Engine interface {
    Check(cfg *sections.Config, rules []Rule) []RuleResult
}

// ============ A3 delivery ============
type DataProvider interface {
    Section() SectionMeta
    Fetch(ctx context.Context, report *DeliveryReport) (any, error) // 返回可渲染 ViewModel
}

type Builder interface {
    Register(p DataProvider)
    Build(ctx context.Context, report *DeliveryReport) (*RenderedReport, error)
}

type Renderer interface {
    Format() string          // html / md / csv
    Render(r *RenderedReport) ([]byte, error)
}

// ============ A4 change ============
type UndoDeriver interface {
    Derive(cmd string, vendor string) (undo string, confidence string)
}

type Pipeline interface {
    PreCheck(ctx context.Context, cr *ChangeRequest) error
    Execute(ctx context.Context, cr *ChangeRequest) (runID string, err error)
    Verify(ctx context.Context, cr *ChangeRequest) (*VerifySummary, error)
    Rollback(ctx context.Context, cr *ChangeRequest) (runID string, err error)
}

// ============ A5 acceptance ============
type Extractor interface {
    Extract(raw string, rule string) (string, error)
}

type Judge interface {
    Judge(actual string, item *AcceptanceItem) (status string, err error)
}
```
