## 阶段一 后端正确性补强（P2 + 3 项低危）

> 特点：改动小、无框架签名变更、可独立合入；**不涉及 Wails 绑定**。

### 1.1 三阶段判定路径补齐产物登记

- **现状（证据）**：[`internal/taskexec/inspection_executor.go:133`](file:///d:/Document/Code/NetWeaverGo/internal/taskexec/inspection_executor.go) `executeCheckOnly` 仅写 `InspectionResult` 库表；而单阶段路径 [`executeInspectionUnit`](file:///d:/Document/Code/NetWeaverGo/internal/taskexec/inspection_executor.go) 在 `:350` 登记 `raw_output`、在 `:423–440` 生成并登记 `inspection_report.csv` / `inspection_report.json`（`ArtifactTypeInspectionReport`）。
- **修改要点**（在 `executeCheckOnly` 结果持久化之后、`completeUnitExecution` 之前）：
  1. 对每个命中命令：从 `holder.GetCommandEcho(deviceIP, cmd)` 取回显 → `e.pathManager.GetInspectionRawFilePath(taskID, deviceIP, <cmd>.txt)` 写盘 → `createArtifactWithResult(taskID, stageID, unit.ID, ArtifactTypeRawOutput, deviceIP+":"+cmd, rawPath)`。
  2. 复用 `inspection.ExportInspectionResultsCSV/JSON(results)` 生成报表 → 写盘 → 以 `ArtifactTypeInspectionReport` 登记。
  3. 产物登记失败**仅告警不阻断**（`createArtifactWithResult` 内部已 `logger.Warn` 并返回 err；调用点保持 `_ =` 忽略，与单阶段一致）。
- **验收标准**：
  - `InspectionPipelineMode=three_stage` 运行时，任务产物列表包含每设备的 `raw_output` 与 `inspection_report.csv` / `inspection_report.json`，与 `single` 模式可见性一致；
  - 判定结果（`InspectionResult` 行数与状态）无任何变化。
- **测试**：在 [`inspection_pipeline_test.go`](file:///d:/Document/Code/NetWeaverGo/internal/taskexec/inspection_pipeline_test.go) 新增用例——三阶段跑通后，断言 `task_artifacts` 中存在 `raw_output` + 2 个 `inspection_report` 记录，且数量 = 设备数 × 对应产物数。
- **风险/回滚**：纯新增登记，无数据迁移；异常时产物缺失不影响判定，回滚即撤销本段代码。

### 1.2 `runDataStore` 满载告警

- **现状（证据）**：[`internal/taskexec/run_data_holder.go:46-52`](file:///d:/Document/Code/NetWeaverGo/internal/taskexec/run_data_holder.go)（`SetCommandEcho`）与 `:94-96`（`SetParsedRows`）在超 64MB 时置 `s.full = true` 后直接 `return`，无任何日志。
- **修改要点**：
  1. 让 `newRunDataStore` / `runDataRegistry` 持有 `runID`（`GetRunData(runID)` 已有入参），以便日志可定位运行；
  2. 在**首次**由 false→true 的临界点输出一次 `logger.Warn("TaskExec", runID, "运行内存快照已达上限 %dMB，后续数据将回退读盘: module=%s", maxRunDataBytes/1024/1024, module)`；
  3. `logger.Warn` 签名见 [`internal/logger/logger.go:109`](file:///d:/Document/Code/NetWeaverGo/internal/logger/logger.go)（`Warn(module, ip, format, args...)`）。
- **验收标准**：构造超限场景时日志恰好出现一次 Warn，含 `runID` 与触发来源；不改变丢弃语义（Stage2/3 仍回退读盘）。
- **测试**：`run_data_holder` 新增单测——注入超过 `maxRunDataBytes` 的数据，断言 `full` 置位且不 panic；日志通过 `logger` 的测试钩子或计数器断言（若现有 logger 无钩子，则以行为断言为主，日志为可观测性增强）。
- **风险/回滚**：极低；仅新增日志。

### 1.3 采集阶段 `doneSteps` 精度

- **现状（证据）**：[`internal/taskexec/inspection_pipeline.go:200`](file:///d:/Document/Code/NetWeaverGo/internal/taskexec/inspection_pipeline.go) `doneSteps := len(unit.Steps)`——即便 `:189` 命令执行异常、或 `:185` 空命令被跳过，也按满额计。
- **修改要点**：改为累加**实际成功执行**的命令数：
  ```
  successSteps := 0
  for _, step := range unit.Steps {
      cmd := strings.TrimSpace(step.Command)
      if cmd == "" { continue }                 // 与现有 continue 语义一致
      echo, cmdErr := exec.ExecuteCommandSync(...)
      if cmdErr == nil { successSteps++ }        // 仅成功才计入
      holder.SetCommandEcho(deviceIP, cmd, echo)
      // …写 raw 文件（保持现状：失败也落盘，便于排查）
  }
  doneSteps := successSteps
  ```
- **验收标准**：Unit 进度条 `doneSteps / totalSteps` 反映真实成功数；Unit 终态仍为 `Completed`（**不因个别命令失败而降级**，设备级容错策略不变）。
- **测试**：单测注入 1 条失败命令（mock 执行器返回 error），断言 `doneSteps == n-1`，Unit 状态仍 `Completed`。
- **风险/回滚**：仅展示精度；若上游依赖「满载」假设计算百分比，需同步检查前端 `progressPercent`（[`TaskExecution.vue`](file:///d:/Document/Code/NetWeaverGo/frontend/src/views/TaskExecution.vue) 中 `doneSteps` 参与 `deviceUnitPriority` 排序，不影响主进度）。

### 1.4 正则标志函数收敛

- **现状（证据）**：两处语义 100% 相同（m/i/s → `(?mis)`，去重，已含 `(?` 前缀则不重复加）：
  - [`internal/ui/parse_template_service.go:551 applyRegexFlags`](file:///d:/Document/Code/NetWeaverGo/internal/ui/parse_template_service.go)
  - [`internal/parser/tree_engine.go:204 buildRegexWithFlags`](file:///d:/Document/Code/NetWeaverGo/internal/parser/tree_engine.go)
- **修改要点**：
  1. 在 `parser` 包导出 `BuildRegexWithFlags(pattern, flags string) string`（`buildRegexWithFlags` 改为其薄包装或直接重命名 + 保留内部别名）；
  2. `ui/parse_template_service.go` 删除私有 `applyRegexFlags`，改调 `parser.BuildRegexWithFlags`。
  - 依赖方向安全：`ui` 已 import `parser`（同文件 `:512 parser.EngineRegex` / `:521` 使用），无循环依赖风险。
- **验收标准**：`grep` 全仓仅剩一处实现；行为等价（同一输入输出逐字节一致）。
- **测试**：`parser` 包补表驱动单测——`("", "mis")`、`("x", "mii")`（去重）、`("(?i)x", "i")`（不重复加前缀）、空 flags 原样返回。
- **风险/回滚**：极低；注意保留「空 flags 直接返回原 pattern」的语义（与 `buildRegexWithFlags` 首行一致）。
- **备注**：本项为「快速收敛」；阶段二 2.1 完成后，UI 将改为直接委托 parser 收集匹配，`applyRegexFlags` 调用点会自然消失（见 2.1）。

## 阶段二 后端能力补强（子规则高亮 + 报表多语言 + 文案种子）

### 2.1 子规则命中高亮（透传 `baseOffset`）

- **现状（证据）**：
  - [`internal/ui/parse_template_service.go:516-530 collectParseMatches`](file:///d:/Document/Code/NetWeaverGo/internal/ui/parse_template_service.go) 在 `EngineTree` 分支显式 `if strings.TrimSpace(r.ParentItem) != "" { continue }`——**只收集根规则**命中；
  - 树引擎 [`internal/parser/tree_engine.go:224 fillSubResult`](file:///d:/Document/Code/NetWeaverGo/internal/parser/tree_engine.go) 递归抽取子节点时未回传子串相对全文的 `baseOffset`。
- **修改要点（推荐「彻底方案」，一举解决 §5 #5 并消除 1.4 的遗留调用点）**：
  1. `parser` 包新增导出的匹配收集能力，如 `func (e *TreeEngine) CollectMatches(rawText string) []Match`，内部：
     - 根规则命中用其在全文中的绝对偏移；
     - 递归 `fillSubResult` 时传递 `baseOffset`（分块/子正则命中位置 + 父块起始偏移），产出**绝对偏移**区间；
     - 返回 `Match{Rule, Start, End, Text}`（`Rule` 用 `ParseItem` 或路径标识）。
  2. `ui.collectParseMatches` 的 `EngineTree` 分支改为调用 `CollectMatches` 并映射为 `models.ParseMatch`；**删除**本地 regex 编译与 1.4 的 `applyRegexFlags` 调用。
  3. `EngineRegex` / `EngineAggregate` 分支保持不变（本就用绝对偏移）。
- **验收标准**：嵌套子规则（如 slot→daughterboard）命中在「匹配高亮」视图中被切段高亮；高亮区间与原文逐字符一致（偏移无漂移）；根规则行为与改造前一致。
- **测试**：
  - `parser` 包：构造含嵌套子规则的树配置，断言子命中 `Start/End` 指向原文正确区间；
  - `ui` 包（[`parse_template_matches_test.go`](file:///d:/Document/Code/NetWeaverGo/internal/ui/parse_template_matches_test.go)）：断言子规则命中被收集且 `Text == rawText[Start:End]`。
- **风险/回滚**：中（递归偏移计算易错）——用「偏移自校验」断言（`Text == raw[start:end]`）兜底；回滚保留根规则分支即可。
- **依赖**：建议在 1.4 之后实施（复用同一导出点）。
